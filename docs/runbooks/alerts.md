# Alert runbook

Every alert links to a section of this page (`runbook_url`). Each section answers: what does it mean,
what to check first, what usually causes it, how to fix it.

Alerts are generated by [`scripts/generate_alerts.py`](../../scripts/generate_alerts.py) from the SLOs in
[`scripts/slo_definitions.py`](../../scripts/slo_definitions.py). See [How alerting works](#how-alerting-works) at the end.

Open the tools:

```bash
kubectl -n monitoring port-forward svc/kube-prometheus-stack-alertmanager 9093:9093       # http://localhost:9093
kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80              # http://localhost:3000
```

## SLO alerts (symptoms)

Two alerts per SLO: `...BudgetBurnFast` (**critical**, act now) and `...BudgetBurnSlow` (**warning**, look soon).
A firing fast burn silences the slow burn of the same SLO in Alertmanager.

### store-availability

**SLO:** 99% of UI requests end without a 5xx status.

1. Dashboard **Incident Lab / Retail Store** → **Error ratio (5xx) by service**: which service fails first? The UI only passes errors on.
2. `kubectl -n retail-store get pods` - restarts, `Pending`, not ready?
3. Logs of the failing service: `kubectl -n retail-store logs deploy/<service> --tail=100`.
4. Did something change? Check the **Rollouts** and **Chaos injected** annotations.

**Usual causes:** a failing backend (orders, carts, catalog), a data store down, a bad rollout.
**Fix:** restart or roll back the failing service (`kubectl rollout restart` / `kubectl rollout undo`), fix its dependency.
**Practice:** [orders-http-500](../../chaos/scenarios/level-1-application/orders-http-500/), [catalog-db-pod-kill](../../chaos/scenarios/level-2-kubernetes/catalog-db-pod-kill/), [ui-bad-deploy](../../chaos/scenarios/level-2-kubernetes/ui-bad-deploy/).

### store-latency

**SLO:** 95% of UI requests are faster than 1 s.

1. **Latency by service**: which service got slow? The slowest dependency is usually the cause.
2. **Saturation** row: CPU throttling, memory near the limit, a node full?
3. Is a dependency unreachable (timeouts)? Check the logs of the slow service.

**Usual causes:** a slow backend, CPU throttling, network problems between services.
**Practice:** [catalog-latency](../../chaos/scenarios/level-1-application/catalog-latency/), [checkout-redis-network-loss](../../chaos/scenarios/level-2-kubernetes/checkout-redis-network-loss/).

### assistant-availability

**SLO:** 95% of questions get an answer (no LLM error, no step limit).

1. Dashboard **Incident Lab / AI Assistant** → **LLM calls / s by result**: which `error_type`? `429` rate limit, `529` overloaded, `401` bad key, `timeout`, `connection`.
2. **Retry amplification**: are SDK retries adding load?
3. `kubectl -n ai-assistant logs deploy/ai-assistant --tail=50`

**Usual causes:** the LLM provider rate-limits or fails, a wrong API key, the gateway is down.
**Fix:** provider-side problems cannot be fixed in the cluster: reduce traffic, wait, raise the quota; fix the key Secret.
**Practice:** [llm-rate-limit](../../chaos/scenarios/level-1-application/llm-rate-limit/).

### assistant-latency

**SLO:** 95% of questions are answered within 30 s.

1. Compare **LLM latency (successful calls)** with **Tool latency p95 by tool**: is the LLM or a tool slow?
2. **Agent steps per answer**: does the agent need more steps than usual?
3. **Tokens per call p95**: longer prompts take longer.

**Usual causes:** a slow LLM provider, slow tools (catalog), more agent steps.
**Practice:** [llm-slow](../../chaos/scenarios/level-1-application/llm-slow/).

### assistant-tool-quality

**SLO:** 95% of tool calls return data, not an error.

This catches a silent failure: the assistant still answers with HTTP 200, but the answers are built on failed tools.

1. **Tool calls / s by tool and outcome**: which tool fails?
2. The tools call the catalog: dashboard **Incident Lab / Retail Store**, catalog latency and errors.
3. Ask the assistant yourself and read the answer.

**Usual causes:** the catalog is slow (over the 5 s tool timeout) or down.
**Fix:** fix the catalog, not the assistant.
**Practice:** [ai-tool-cascade](../../chaos/scenarios/level-1-application/ai-tool-cascade/).

## Cause alerts (warnings)

### DataStoreNotReady

A database, cache or queue pod of the store is not ready for over 1 minute.
Check `kubectl -n retail-store describe pod <pod>` and its logs. Data stores use `emptyDir`: after a restart they are **empty**,
and the services that seed data at startup (catalog) must be restarted.
**Practice:** [catalog-db-pod-kill](../../chaos/scenarios/level-2-kubernetes/catalog-db-pod-kill/).

### PodMemoryNearLimit

A pod uses over 90% of its memory limit for 5 minutes. At 100% it is OOM-killed.
Check **Memory, % of limit** and **Container restarts**. Raise the limit or find the memory growth (load, leak).

### LlmRetryAmplification

The LLM API receives over 1.5 requests per LLM call: the SDK retries failing calls (429, 529, 5xx, timeouts).
Retries make an overloaded provider worse. See [assistant-availability](#assistant-availability).

### LlmCostBudgetExceeded

Estimated LLM spend is above the hourly budget (`LLM_HOURLY_BUDGET_USD` in `generate_alerts.py`).
Check traffic, **Tokens per call** and **Agent steps per answer**. A looping agent or very long prompts multiply the cost.
Fires only when the gateway talks to the real Anthropic API; in mock mode the estimated cost is ignored.

## How alerting works

**Hybrid:** symptoms use SLOs with burn-rate alerts, causes use plain thresholds.

**Burn rate** = error ratio / error budget. With a 99% SLO the budget is 1% errors; 14.4% errors burn it 14.4x too fast.
The method is the multiwindow, multi-burn-rate alerting of the [Google SRE workbook](https://sre.google/workbook/alerting-on-slos/),
with all windows **scaled down 12x** so alerts fit a 1-2 hour practice session:

| Alert | Burn rate | Google windows | Lab windows |
|---|---|---|---|
| fast (critical) | 14.4x | 1h and 5m | 5m and 1m |
| slow (warning) | 6x | 6h and 30m | 30m and 5m |

The long window proves the problem is real, the short one that it is still happening, so alerts clear quickly after a fix.
Alerts also need at least 10 events in the long window, so a few errors at very low traffic do not page.

Measured on a local run (1 question per second, then HTTP 429 from the LLM): the slow-burn warning fired after 60 s,
the fast-burn page after 150 s (the 5-minute window still held the healthy minute before the failure),
and the page cleared about 50 s after recovery.
